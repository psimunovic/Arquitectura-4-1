Introducción al Modelo 4+1 de Philippe Kruchten

El Modelo de Vistas de Arquitectura 4+1 fue diseñado por Philippe Kruchten en 1995 para describir la arquitectura de sistemas de software basados en el uso de múltiples vistas concurrentes. Cada vista aborda un conjunto específico de preocupaciones del sistema desde la perspectiva de diferentes involucrados (stakeholders).

¿Por qué usar 4+1?

Permite descomponer la complejidad del software organizando los requerimientos y soluciones en 5 perspectivas fundamentales: Lógica, Desarrollo, Procesos, Física y Escenarios.

Vista Lógica: Concepto y Fundamentos

La Vista Lógica atiende los requerimientos funcionales del sistema. Muestra cómo se organiza conceptualmente el sistema en términos de clases, objetos, interfaces y sus interacciones relacionales.

    Audiencia principal: Usuarios finales, analistas de negocio y diseñadores de software. Enfoque: Abstracción, encapsulamiento, herencia y modularidad.
Página 3 / 25

Vista Lógica: Diagrama de Clases - Componentes

El Diagrama de Clases es la estructura principal de la vista lógica. Sus componentes esenciales son:

1. Clase

Representa una entidad con atributos (datos) y métodos (comportamiento).

2. Relación de Asociación

Enlace estructural entre dos clases (1..*, 1..1).

3. Composición y Agregación

Relaciones "todo-parte". La composición implica fuerte dependencia de ciclo de vida.

4. Herencia / Generalización

Permite a una subclase heredar atributos y métodos de una superclase.

Página 4 / 25

Vista Lógica: Ejemplo Diagrama de Clases

classDiagram
    class Usuario {
        +int id
        +string nombre
        +string email
        +login()
    }
    class Pedido {
        +int idPedido
        +date fecha
        +float total
        +calcularTotal()
    }
    class Producto {
        +int idProducto
        +string nombre
        +float precio
    }
    Usuario "1" -- "0..*" Pedido : realiza
    Pedido "1" *-- "1..*" Producto : contiene

Explicación del Diagrama:

Un Usuario puede realizar de 0 a muchos Pedidos. Un Pedido está compuesto de 1 o más Productos (Relación de Composición *--).

Página 5 / 25

Vista Lógica: Diagrama de Comunicación - Componentes

El Diagrama de Comunicación enfatiza la organización estructural de los objetos que envían y reciben mensajes.

    Objetos/Roles: Instancias de clases representadas por rectángulos. Vínculos: Líneas sólidas que conectan los objetos interactuantes. Mensajes Numerados: Indican la secuencia de ejecución implícita (ej. 1: verificar, 1.1: consultar).

Vista Lógica: Ejemplo Diagrama de Comunicación

graph LR
    Cliente[Cliente] -->|1: solicitarPago()| GestorPago[Gestor de Pagos]
    GestorPago -->|2: validarTarjeta()| Banco[Pasarela de Banco]
    Banco -->|3: respuestaOK()| GestorPago
    GestorPago -->|4: confirmarReserva()| BD[(Base de Datos)]

Explicación de Elementos:

Muestra el flujo estructurado: 1. El cliente solicita pago al gestor; 2. El gestor valida con la entidad bancaria; 3. La respuesta retorna; 4. Se confirma el registro en la BD.

Página 7 / 25

Vista de Desarrollo: Concepto y Fundamentos

También conocida como Vista de Implementación. Muestra la organización de los módulos de software en el entorno de desarrollo (bibliotecas, paquetes, subsistemas y ejecutables).

Audiencia: Programadores, testers y gestores de configuración.

Página 8 / 25

Vista de Desarrollo: Diagrama de Componentes

Describe la organización física y las dependencias de los componentes de software.

Componente: Unidad ejecutable o biblioteca de código.
Interfaz Provista (Lollipop): Servicios ofrecidos por el componente.
Interfaz Requerida (Socket): Servicios requeridos para su funcionamiento.

Vista de Desarrollo: Ejemplo Diagrama Componentes

graph TD
    subgraph Frontend
        UI[UI Web App - React]
    end
    subgraph Backend API
        Auth[Módulo Autenticación]
        OrderMod[Módulo de Pedidos]
    end
    subgraph Capa Datos
        DBServer[(PostgreSQL)]
    end

    UI ..> Auth : API REST / JSON
    UI ..> OrderMod : API REST / JSON
    OrderMod ..> DBServer : SQL Driver

Explicación del Diagrama:

El módulo de UI Frontend depende funcionalmente de las API REST expuestas por Autenticación y Pedidos. Pedidos a su vez se comunica con el motor PostgreSQL.

Página 10 / 25

Vista de Procesos: Concepto y Fundamentos

Aborda los aspectos dinámicos del sistema en tiempo de ejecución: concurrencia, distribución, rendimiento, escalabilidad y sincronización de hilos/procesos.

Audiencia: Integradores de sistemas y arquitectos de rendimiento.

Página 11 / 25

Vista de Procesos: Diagrama de Actividad

Utilizado para modelar flujos de trabajo paso a paso y estados de ejecución.

    Nodo Inicial/Final: Comienzo y fin del proceso. Actividades: Acciones ejecutadas en el flujo. Bifurcaciones (Decisión): Caminos condicionales. Barras de Sincronización (Fork/Join): Ejecución concurrente.

Página 13 / 25

Vista de Procesos: Diagrama de Secuencia

Modelado temporal de llamadas y mensajes intercambiados entre instancias en el tiempo.

Líneas de Vida: Existencia del objeto en el tiempo.
Mensajes Síncronos: Esperan respuesta inmediata.
Mensajes Asíncronos: No bloquean la ejecución.
Barra de Activación: Muestra el tiempo en ejecución activa.
Página 14 / 25

Vista de Procesos: Ejemplo Diagrama de Secuencia

sequenceDiagram
    autonumber
    actor U as Usuario
    participant API as Backend API
    participant DB as Base de Datos

    U->>API: POST /api/login (usr, pass)
    activate API
    API->>DB: SELECT * FROM usuarios WHERE ...
    activate DB
    DB-->>API: Datos Usuario / Hash
    deactivate DB
    API-->>U: 200 OK + JWT Token
    deactivate API

Explicación del Diagrama:

Flujo secuencial ordenado en el tiempo para la generación de token de autenticación desde el usuario hasta la base de datos.

Vista Física: Concepto y Fundamentos

Mapea los componentes de software sobre los nodos de hardware, incluyendo la infraestructura de red y topología de despliegue.

Audiencia: Ingenieros DevOps, administradores de red y arquitectos de infraestructura.

Página 16 / 25

Vista Física: Diagrama de Despliegue

Describe la arquitectura física en hardware donde se ejecuta la solución:

    Nodo: Recurso computacional (servidor físico, máquina virtual, contenedor). Artefacto: Archivo ejecutable, JAR, contenedor Docker desplegado dentro del nodo. Conexión: Protocolo de enlace de red (HTTP/HTTPS, TCP/IP, JDBC).

Vista Escenarios (+1): Concepto y Casos de Uso

La vista "+1" o Escenarios sirve para unir y validar las otras 4 vistas. Consiste en una pequeña cantidad de casos de uso fundamentales que ilustran el comportamiento integral del sistema.

Propósito: Validar la coherencia global de la arquitectura trazada.

Ejercicio Integrador: Caso de Estudio "MediQuick"

Enunciado del Caso:

Diseñe la arquitectura 4+1 para la plataforma de telemedicina MediQuick. Los pacientes solicitan citas médicas en vivo, los médicos atienden por videollamada y las recetas digitales se generan en formato PDF firmado. El sistema requiere alta disponibilidad y cumplimiento normativo estricto de seguridad de datos de salud.

Desafío para el estudiante:

Analice las vistas en las páginas siguientes para comprender la solución arquitectónica integral propuesta.
